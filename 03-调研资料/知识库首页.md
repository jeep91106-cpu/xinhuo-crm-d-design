# 薪火 CRM · 知识库首页

广告流量代理公司内部 CRM（RuoYi-Vue 3.8.2，Spring Boot + MyBatis + Vue2）的 Obsidian vault。上游以**巨量引擎**为主；公司为**直客**（广告主本人）或**渠道**（同行代理，名下多个投流客户）开广告账户、垫款充值、代运营。

用户群：销售商务、媒介（开户/充值）、财务、老板。系统 2026-07-06 上线，快照日 2026-09-14。

## 一句话结论（2026-09-14 分析）

1. **「抖音事业部」与「其他媒体」可以且应当合并**：Service/Mapper/表本来就是一套，只有 Controller 薄壳和 Vue 页面各复制一份；两边装的都是巨量本地推/巨量AD，差别只是账户开在自有端口还是外部代理商。→ [[抖音事业部-vs-其他媒体-合并分析]]
2. **商务基本不用系统**：纯商务 14 人里 12 人零登录；数据由 1 个 AE + 5 个开户媒介代录；充值/转户/退币 80%–100% 通过微信群机器人完成。→ [[系统使用现状-证据链]]
3. **「不能回填」的根源**：开户申请把主体/店铺/供应商存成自由文本，自有端口的开户回复不建账户，媒介要再录一遍账户 ID；每笔充值必填前返/后返而非默认带出。→ [[角色×字段×阶段-流程图]]
4. **财务链没闭环**：现金收款 142/145 待确认，对账单 19/225 完成，授信审批 254 单全部「直接过不审批」。
5. 用户口述的商务/媒介字段（直客ID、来客ID、纵横ID、代理商ID、社会信用代码、开户银行、住所）**现系统一个都没有**，需在重构中新增。

## 用户已确认的决策（2026-09-14）

| 问题 | 用户决定 | 对方案的约束 |
|---|---|---|
| 腾讯K4 / 快手 与三棵停用事业部树 | **先不删除** | 合并方案保留「媒体产品」维度（巨量本地推 / 巨量AD / 腾讯 / 快手），停用树只隐藏不清理 |
| 外转渠道收缩 | **收缩了也不停止** | 外转消耗导入入口、NOAGENT 供应商记账路径必须保留 |
| 12 个零登录商务账号 | **不重要，后续重新迁移数据、重做权限和角色** | 角色/权限按重构重建，不以现有 `sys_role` 为基线 |
| 微信机器人群 / 现金到账记录 | **目前混乱，后期重构** | 机器人与现金收款链路列入重构范围，不在现系统上修补 |
| 「直客」是什么 | **客户就是客户，直客只是一种 ID 字段** | 不新增实体；`直客ID` 作为主体记录上的巨量客户编号字段，客户层保持不变 |
| 商务 / 开户媒介的字段清单 | 已给出（本地推 vs 非本地推两组主体字段；账户层 + 供应商层媒介字段） | 已按巨量逻辑映射到六条真实样例：[[多状态整条数据样例]] |
| 一个主体多种业务类型（2026-09-15） | **原来就有，不改业务方式，保持原逻辑** | 不加互斥约束；业务类型继续由每个广告账户的 `type` 决定 |
| 数据结构（2026-09-15） | **不重构整体数据逻辑** | 客户 → 主体 → 店铺 → 广告账户 四层不动，只在现有表上加字段（资质、直客 ID、来客 ID、纵横 ID、代理商 ID、开户行） |
| 一个主体多个直客 ID（2026-09-15） | 事实确认 | 直客 ID 不能是主体表单列；落在开户申请 → 广告账户，主体页汇总。产生规则待确认（是否每个供应商端口一个） |
| 归属与流转人（2026-09-15） | **由企业微信组织 + 后台工作流配置决定**：主流程 商务 → 开户媒介 → 充值媒介 → 财务，中间部门与颗粒度可配置（如沈阳人员走沈阳组织） | 不再设计静态"归属渠道/负责商务/媒介"字段；每步经办人由流程实例记录 |
| 来客 ID 由商务填、流转到媒介、媒介可改（2026-09-15） | 用户提议，**评估可行** | 现状已是如此（190 张开户申请里 141 张填了 19 位来客 ID），加校验、落店铺、改动留痕、API 校验四条护栏 |

待用户确认：一个主体多个直客 ID 的产生规则——同一家公司在不同供应商/端口各开一次、每个端口一个直客 ID？还是同一端口下也会有多个？（决定直客 ID 挂在账户还是需要主体-供应商子表）
