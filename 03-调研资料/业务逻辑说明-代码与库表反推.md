# 业务逻辑说明 — 从代码与库表反推

范围：薪火 CRM（RuoYi-Vue 3.8.2，Spring Boot + MyBatis + Vue2/Element）后端 `ruoyi-digital` 模块的业务规则。来源标注：`代码` = 反编译 Java（`D:\CodexWorkspace\xinhuo-crm\decompile\src-utf8`），`库` = 生产快照实测，`配置` = `sys_config` / `sys_dict_data` / `base_approval_process`。本文只写现状，不写建议；建议见 [[抖音事业部-vs-其他媒体-合并分析]] 与 [[角色×字段×阶段-流程图]] 末节。

## 1. 业务对象与层级

```
供应商 dig_supplier ──┐
客户 dig_customer ── 主体 dig_customer_subject ── 店铺 dig_shop ── 广告账户 dig_advertising_account
   │ 钱包 ×2 dig_customer_wallet                                     │ 日消耗 dig_*_account_consume
   │ 流水 dig_customer_bill                                          │ 充值 / 转户 / 退币
   └ 对账单 dig_customer_statement
```

| 对象 | 业务含义 | 关键规则（来源） |
|---|---|---|
| 客户 | 付钱、拿返点、享授信的主体；标签 直客 / 渠道（同行代理） | 名称唯一性只在同 `types` 内校验（代码 `DigCustomerServiceImpl:1316`）；`types` 由创建入口写死（代码 各平台 Controller） |
| 主体 | 广告主营业执照公司；媒体端开户资质挂在主体上 | 一客户多主体；`isapi` 标记是否 API 端口主体（库 53%） |
| 店铺 | 主体下的门店/店铺（本地推场景下对应抖音来客门店） | `@NotNull subjectId, shopName`；`shop_no` 外转可空（代码 `DigShop`）；68% 名 = 主体名（库） |
| 广告账户 | 媒体侧投放账户 ID | `type` 决定媒体产品与渠道（字典 `ks_account_type`）；`supplier_id` 决定走 API 还是记账 |
| 供应商 | 账户从哪开出：自有端口（`suppliertype=AGENT`，有 `dy_agentId` 指向 `dig_dy_developinfo`）或外部代理商（`NOAGENT`） | `pay_type`、`main_wallet_id`（代理大钱包）、`threshold` 余额预警（代码 `BaseUtils.remindAgentBalance`） |
| 钱包 | 每客户「一类」「二类」两个钱包，各自有余额与前返/后返 | 现金收款、充值必须指定 `wallet_key`；未指定报「客户有多个钱包，请设置收款的钱包」（库 33 次） |

系统公共客户：`RuoYiConfig.getDouyincustomerId()` / `getTencentcustomerId()` 各指向一个 `types`=2/3/4 的占位客户，不允许改删（代码 各 Customer Controller）。

## 2. 资金模型

三种「钱」：

| 名称 | 存在哪里 | 进 | 出 |
|---|---|---|---|
| **现金备款** `customer.balance` / 钱包 `balance` | 客户层 | 现金收款确认（`DigCashrechargeServiceImpl` 确认 → `CustomerBill` 类型 1） | 账户充值 `cash_pay`、退现、客户转账 |
| **授信（垫款）** `credit_money` 额度 / `credit_usemoney` 已用 | 客户层 | 授信申请通过（永久 12 / 临时 22）；回款时 `credit_usemoney` 减 | 账户充值 `credit_pay`（库：96% 的充值走授信，现金支付仅 5%） |
| **货币** `account.currencymoney` | 账户层（媒体账户里可消耗的钱） | 充值 `currency_recharge`、转入、后返货币 | 消耗、转出、退币 |

**返点换算**（代码 `DigAdveracoountRechargeServiceImpl`）：
- 前返：`currency_recharge = cash_recharge × (1 + before_ratio)`，充值时立即多给货币。
- 后返：按 `after_ratio` 记 `after_currency`，事后以「后返货币 / 后返款」形式返还（流水类型 14）。
- 账户返点 `account_ratio` 与客户返点分层；配置 `rebateLimit` 限制各账户类型返点上限（`t102:4,t1001:4,t1002:4,t1003:4`）。
- 供应商侧：`actual_expenditure = 付给供应商的钱`，`supplier_ratio` 供应商给公司的返点，差额即毛利。`dig_supplier.arrears` 记欠供应商款。

**服务费**：`service_point`（客户）/ `service_ratio`（消耗行）按消耗计提 `service_spend`，累计 `unsettled_service_fee`，结算记 `settlement_service_fee`；退币可选「抵扣服务费」（`refund_type=1`）。库：客户层 `service_point` 全 0，计提字段主要由 API 消耗行携带。

## 3. 核心流程与状态机

### 3.1 开户申请 `dig_accountopen_apply`
- 新建（代码 `insertDigAccountopenApply`）：必须选客户；`data_type`（1 端内 / 10 端外）≠ 客户 `types` 则抛「申请的客户类型和选择的客户的类型不一致」。申请人/部门自动写入。
- 回复（`replayAccountOpenApply`）：账户列表序列化进 `account_nos`；仅 `data_type=10` 时：按 `supplier_name` 查供应商 → 逐个 `DigAdvertisingAccount`（客户 ID、账户 ID/名称、店铺名缺省=主体名、`type=account_type`、`remark=开户申请创建账户`）→ `batchInsertAdveraccount(list,"10")` → 刷新客户 `account_infojson`。
- 状态 `state`：0 待处理 → 1 已处理（字典 `openaccountstate`）。
- 库：189 单，平均复制数量 11；处理时长自有端口 2.5h、外转 12.9h。

### 3.2 现金收款 `dig_cashrecharge`
- 申请 `@NotNull`：客户、金额、收款账户（公司收支账户 `dig_account`）。
- 确认（财务）：`approval_state` 0 → 1 → 2；写客户流水（类型 1）、更新钱包余额；可撤销（流水 13）。`serialnum` 1 新单 / 2 首续 / 3 续费 供提成用。
- 库：145 单 142 停在 0。

### 3.3 账户充值 `dig_adveracoount_recharge`
1. 发起：PC（商务/媒介选账户填金额）或微信机器人（群消息解析）。`@NotNull`：现金金额、前返点数、后返点数。
2. 系统算：货币金额、授信/现金拆分、供应商应付、写 `wallet_json` 快照、`credit_usemoney` 与 `account_balance` 快照。
3. 媒介确认 `confirmAccountRecharge` / `douyinConfirmAccountRecharge`：
   - 供应商 `AGENT`：取 `dy_agentId` → `dig_dy_developinfo` 的 access_token → `DouyinApiUtils.sendWalletRecharge(main_wallet_id → account_no, amount, AGENT)`；成功 `sync_state=30`，回写 `agenttotalBalance` 并按 `threshold` 预警。
   - 供应商 `NOAGENT`：不调 API，直接记账（外转由外部代理商人工划款）。
   - 快手路径（`DigKuaishouJinfu`，有 token 走 API、无 token 走 Cookie 模拟）已停用。
4. 状态 `approval_state`：0 待确认 → 1 媒介确认 → 2 已完成；5 拒回（`refuse_reason`）。`supplement_state` 补单标记。
5. 修改已完成的充值走「充值/退币调整」审批（流程 16，`dig_edit_accountrecharge`）。
- 库：1,283 单；已完成 1,112、拒回 108、待确认 24；机器人 1,032 / PC 256。

### 3.4 转户 `dig_transfer_account`
- 同客户账户间货币平转（配置 `transferConversion=equipoise`，`crossCustomer=0`）；`transfer_type` 巨量方向枚举；自有端口调 API，否则记账。审批流程 2（配置存在，实际由机器人直接执行，87 单 100% 机器人）。

### 3.5 退币 `dig_return_coin`
- 账户货币退回：`refund_type` 0 退到客户备款 / 1 抵扣服务费；`is_all` 全退时按 API 余额取整（代码 `ExternalApiServiceImpl:703-836` 按账户类型选 API）。状态 + `sync_state`。审批流程 4。库 94 单，85% 机器人。

### 3.6 退现 `dig_return_money`
- 客户备款退回银行账户：`ReturnMoneyStatus` 0 未付款 / 1 已付款；审批流程 3（财务部 0–999,999）。库 0 单。

### 3.7 授信 / 返点 / 备款调整
- 授信 `dig_customer_limit_apply`：`datatype` 1 永久 / 2 临时；申请值、回款周期（`return_type`：按周/按月/固定日）、合同附件；通过后写客户 `credit_money`、`credit_limit_type`、`next_return_time`。库 254 单全部 `approval_state=3`（`ApprovalState.COMPLETE` 直接过不审批）。
- 返点 `dig_cus_operratio`：前返/后返调整，流程 18（厦门财务部）；前返变动会生成 `datatypes=1` 的充值记录记录余额变动。库 265 单。
- 备款调整 `dig_cus_operbalance`：页面标「无需审批实时生效」。库 14。

### 3.8 消耗
- 自有端口：定时任务按 `dig_dy_developinfo` 拉巨量账户日消耗到 `dig_douyin_account_consume`（含 `business_type` 产品线、`data_type` 自运营/走量、ROI、`agent_id`）；未知账户按 API 自动建账户（remark「根据API拉取消耗信息建立账户」）。
- 外转：Excel 导入 `dig_other_account_consume`（`DigOtherAccountConsumeServiceImpl`）；未知账户 ID 自动建账户 `customerType=10`。
- 供应商 `last_consume_date` / `media_balance` 记录媒体端余额同步。

### 3.9 对账与流水
- 客户流水 `dig_customer_bill`：每个资金动作一条，`business_type` 见枚举；`balance_after` 快照。
- 对账单 `dig_customer_statement`：定时 02:00 按客户生成（`generate_type=automatic`），算 `consume_money`、`arrears`、`return_money`、`overdue`；财务确认 `is_completed=1`。`credit_datatype` 1。库 225 / 19 完成。
- 状态日志 `dig_bussiness_statelog`：现金收款/充值/退币/转户/退现的每次状态变化。

### 3.10 迁移主体（跨媒体）`dig_transfer_subjectapply`
- 把主体（及账户）从一个客户/类型/供应商迁到另一个；申请-处理两步。存在的唯一原因是两棵树按 `types` 隔离。库 33 单。

## 4. 审批引擎

- 配置 `base_approval_process`（流程编号 `approval_no` = `ApprovalRule`）+ `_detail`（金额区间 `min_money~max_money`、`type` 0 人员 / 1 角色 / 2 部门负责人、`sort` 顺序）。
- 现行有效配置（库）：

| 流程 | 区间 | 审批人 |
|---|---|---|
| 12 永久额度 | 0–200,000 | 申请人部门负责人 |
| 12 永久额度 | 200,001+ | 董事长 |
| 22 临时额度 | 0–100,000 | 部门负责人 |
| 22 临时额度 | 200,001+ | 董事长 |
| 18 返点 | 1–100,000 | 厦门财务部 |
| 3 退现 | 0–999,999 | 财务部 |
| 13 客户转账 | — | 厦门财务部 |
| 16 充值修改 | — | 财务部 |

- 但授信申请实测全部 `approval_state=3`，说明代码在某条件下直接置 COMPLETE（`ApprovalProcessType.JUMP=400` 或未命中区间）。> [!hypothesis] 需在本地副本跑一次授信申请复现。

## 5. 微信机器人（实际的「操作入口」）

- `dig_robot_ex`：微信群名 ↔ 客户绑定（库 5 个群），`style_json` 定义回群消息字段（充值：充值时间、账户 ID、账户名称、充值数量、充值单号、账户余额、备款余额、在途金额、退现中、授信已用、总可用金额；退币、转户类似）。
- 入口：`OfficialAccountImpl`（公众号/群消息）→ 解析「充值 / 退币 / 转户 + 账户 ID + 金额」→ 校验账户属于该群客户 → 生成单据（`source=机器人`，登录身份为 RPA 角色账号）→ 调 API → `generateRobot*Msg` 回群 → `robot_send_record` 回执。
- WebSocket（`MyWebSocketHandler`，`RuoYiConfig.isRobotwebsocket()`）推送给机器人客户端发消息。
- 库：充值 80%、转户 100%、退币 85% 来自机器人。

## 7. 数据权限与共享

- RuoYi `@DataScope` 按角色 `data_scope`：商务 5 仅本人（按 `sale_id`），媒介/AE/财务 1 全部，总经理 3 本部门。
- 客户共享：`dig_customer_refuser`（人 ↔ 客户，231）、`dig_customer_refdep`（部门 ↔ 客户，280，`dep_type` 1 运营部 / 2 销售部）。
- 待办计数：`dig_customer_expand` 按客户维护 `cash_pending / return_money_pending / limit_pending / recharge_pending / return_coin_pending / transfer_pending`（字段名以库为准），前端未见使用。
