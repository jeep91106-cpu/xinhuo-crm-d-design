## 1. 背景与价值论证

### 1.1 业务背景与可核实基线

公司现有抖音事业部与其他媒体两条主要业务线，共享内部人员、公共客户资料和财务过程。用户的核心不满是缺少贴合岗位的数据处理与操作方式；重构目标是保留有效业务计算和兼容范围，改善任务办理、信息复用与数据流转。[R03、R05、R16]

| 历史观察 | 证据含义 | 本 PRD 的处理 |
| --- | --- | --- |
| 119 张表、156 项页面/目录配置、494 项动作配置 | 既有调研元数据时间为 UTC 2026-09-21 03:22:10；配置数量不等于可用功能数量 [R04] | 覆盖矩阵逐项对应，不凭菜单标题判已实现 |
| 12,675 条未删除账户相关记录 | 其中 12,672 条普通账户、3 条平台共享钱包记录；统计范围见 R05 | 平台共享钱包是单独对象类型，不能混为普通广告户 |
| 146 组跨旧入口重复账户，共 292 行 | 旧入口隔离存在身份合并风险 [R05] | 新录入拦截真实重复账户；旧冲突先核验，保留原行与关系 |
| 66 条本地推普通账户未匹配店铺 | 旧关系缺失并不等于允许任意补造来客 [R05] | 建立待核对任务与来源映射 |
| 64 张业务表格曾被检查 | 未找到足以确认现行工资/提成制度的权威工作簿 [R14] | 先兼容已核验旧分支，后续模板发布前财务样本复算 |

上述是研究文档中的历史观察，本轮编写没有再登录生产或执行数据库事务。它们用于揭示设计约束，不用于虚构新系统的性能、节省工时或现网损失。

### 1.2 问题、原因和改进方向

| 使用痛点 | 结构性原因 | 产品处理与可验证价值 |
| --- | --- | --- |
| 同客户/主体/店铺重复填写 | 公共资料、账户责任和结算身份混杂 | 先检索路由，再复用资料；一条账户明确展示三类关系 |
| 换业务线就换一套操作逻辑 | 产品、办理路径、供应商与旧入口耦合 | 统一工作台与账户列表，按产品能力动态显示字段；保持原资金分支 |

### 1.3 定位与价值主张

薪火 CRM 是内部广告业务办理及结算协作系统。统一的是资料入口、任务体验、权限与可追溯事实；产品差异、资金属性和已核验计算继续保留。系统承担内部账的可解释性与一致性，不依赖公司其他会计或税务账本打通。

## 2. 目标与成功指标

### 2.0 不做清单

1. 不设置商务个人用款额度、耗用恢复或转授模型；已确认取消，操作留痕保留。
2. 不接管公司会计税务系统或另一套账本，不把外部集成作为内部闭环前提。
3. 不给普通商务开放渠道跨结算客户 CRM 转账。
4. 不赋予渠道商务自行批准客户授信的权力。
5. 不在子广告账户消耗同步时重复扣渠道总账。
6. 不把直客、来客、纵横、广告账户 ID 合成一个通用编号。
7. 不把公共客户、主体、店铺的维护人自动视为广告账户归属人。
8. 不把旧 shop_no 的号长或 WZ 占位直接认定为真实来客。
9. 不把超时和未知结果直接视为失败后释放资金或重试。
10. 不为普通开户固定增加合同、财务或 Boss 审批；实际产品资质与可配置规则另行执行。
11. 不假定各媒体已提供或已打通自动开户、付款和查询接口；保留人工有据办理及接口适配。
12. 不继续生成已暂停的 AI 图片原型；本 PRD 提供可追溯的程序绘制图示和页面结构。

### 2.1 业务目标

让已存在的资料被安全复用，让每项待办有责任人和下一步，让每笔资金与外部业务有唯一事实链，并让已确认的旧核算分支兼容可复算。完整业务范围与开发顺序分开，不能因人事行政后期开发而删除需求。

### 2.2 价值指标与护栏

| --- | --- | --- | --- |

## 3. 用户与场景

### 3.1 角色、责任与工作方式

| 角色 | 主要目标与原痛点 | 本系统入口及职责 | 关键边界 |
| --- | --- | --- | --- |
| 普通商务 | 少重复录入、知道进度；以往多处查档 | 个人工作台、公共资料、开户/充值/退款/续费申请 | 无渠道转账和自行授信批准 |
| 渠道商务 | 管理多主体多账户及渠道总账 | 普通商务能力＋授权渠道资金范围、代客户申请信用 | 角色与渠道客户标签分开；非无限权限 |
| 协办 | 代办指定业务并清楚责任 | 受托任务及授权账户 | 保留实际经办人；不因点击获得归属 |
| 商务主管 | 查看团队积压及交接 | 团队视图、继承/转交与异常处理 | 团队范围由后台配置，不自动拥有财务付款权 |
| 媒介主管 | 依地区均衡派单 | 区域待派、负载、异常升级 | 派单不同于审批；需权限才能亲自办理 |
| 开户媒介 | 资料齐备后办理并回填结果 | 开户队列、批次逐行回填、纵横补资料 | 直客ID随主体维护、可空；媒介可在原单补资料，补录人不成为归属商务 |
| 充值媒介 | 准确执行与确认结果 | 充值/退币/转户队列及核实未知 | 不能把通知已读或接单作为交付成功 |
| 财务确认/核算 | 实际到账、规则、对账可核 | 收款、费用返点、债务核销、对账和开票 | 动作独立授权，发布配置不授予余额改写权 |
| 财务付款 | 实际支出可核销 | 退款、后返、供应商、费用与工资付款队列 | 审批完成不等于已支付；记录真实付款证据 |
| Boss/授权审批者 | 依据金额、用途与版本做决策 | CRM/企微同一审批实例 | 只有有效版本批准并保存 CRM 才生效 |
| 人事/行政/薪酬 | 组织、任职、考勤、工资可衔接 | 人事工作台和权限内薪资页 | 企业微信组织是来源，CRM 角色不是工资岗位 |
| 资料/配置/审计管理员 | 资料、模板和异常可管理 | 后台配置、资料治理、只读审计 | 管理角色不能天然继承业务资金权限 |

一人可以同时拥有多个 RBAC 角色；同一待办去重，数据范围和敏感字段权限按动作明确。岗位、角色、商务归属、财务结算方四者独立。不虚构使用者每天耗时或投诉次数；正式量化画像由 K02 的基线采集补齐。

### 4.2 通用交互约定

全局搜索支持客户、主体、店铺和平台 ID，结果标明对象类型与完整上下文。查询不到、无权限、资料待核对、同步失败四种状态给出不同说明，不能统一显示“暂无数据”。

列表采用固定主键列、可选列、分组筛选、个人视图、批次选择及侧栏详情。操作后返回原筛选、分页和行位置。全筛选选择与本页选择必须区分，批量提交前显示对象数和作用范围。金额显示单位、数据截至时间与可用/冻结/在途含义；完整 ID 可复制，不用科学计数法。

栏目标题和可点击功能页明显区分；提交、补资料后留在原模块及原单，保留筛选和展开状态。未保存离开先提示。保存草稿保留用户已填数据；退回定位到字段和原因；后台产品切换导致不适用的旧值不静默提交。操作禁用说明状态或权限原因，并提供可执行下一步。表格支持键盘焦点、明确错误文字，不仅靠颜色传达状态。

## 5. 业务流程

### 5.1 开户主流程及责任

商务选客户→空搜索立即完整显示本客户主体→优先选择已有主体或查重后新增→自动复用唯一店铺，无店则同页新增；历史多店先核对关系。全局未关联主体必须由用户明确选择才关联，更换客户或主体重新处理下游资料和附件。[R17]

**图 5-1　开户主线泳道**

![图 5-1 开户主线泳道](assets/fig-5-1.png)

图 5-1 的派单与重派仅由媒介主管权限执行，普通媒介只能办理当前指派给本人的原单。后台决定匹配条件及兜底队列。逐行或批量保存结果后进度汇总在原申请，全部录完仍须显式“完成本次开户”；历史已完成保留，纵横待补不阻挡完成。负责商务是业务责任，提交人、协办、开户媒介是实际办理记录；完成点击者不自动取得账户归属。[R01、R06、R12]

### 5.3 资金动作、金额与账务效果

| 事实/动作 | 必须产生的结果 | 禁止的结果 |
| --- | --- | --- |
| 提交收款或上传付款凭证 | 记录待证实和来源；无可用备款变化 | 仅凭提交就可以消费 |
| 财务确认到账 R | 按真实现金用途分配：R=欠款/应收核销D+本金备款B+独立费用F+已接受多款差额A+未分配U；各项互斥不重计，公司现金增加R一次；无费用/多款的本金分支可简写R=D+B+U | 先加R备款再额外还债；把非现金短款减免算进实际到账 |
| 现金充值成功 | 现金冻结转实际扣减，形成平台交付/账户业务记录，按模板计算单位转换 | 现金和广告币按数字直接相加 |
| 信用充值成功 | 在途占用转未偿本金；没有客户真实收款 | 把批准额度当收入或备款 |
| 明确失败 / 结果未知 | 失败释放未发生部分；未知保留在途并查询原请求 | 未知当失败重做；整批释放成功行 |
| 信用还款 | 真实到账核销相应欠款；适用循环信用恢复可支用权 | 恢复额度另计一笔现金 |
| 渠道出资给其他客户账户 | 渠道总账扣一次；保留资金方和目标账户归属 | 目标客户再加备款，或后续消耗再扣渠道一次 |
| 普通渠道 CRM 转账 T | 源 −T、目标 +T，同单位；公司现金净变化0 | 半笔入账、未使用授信作为现金转出 |
| 旧资方转账分支 | 转入=M×(1+客户返点/100)；转出=M×(1+资方返点/100)；差额有独立科目/去向并整体守恒 | 把差额消失，或把本分支套给所有普通转账 |
| 平台退币 | 核实平台退回后按原资金来源、返点及费用规则处理 | 提交退币立即加备款；信用来源退回虚构现金 |
| 客户现金退款 | 冻结可退数→财务实际付款→确认真实结果→核销 | 审批通过就标已付；重复回调再次扣钱 |
| 后返实际支付 / 转备款 / 抵欠款 | 按选择路径核销应返；保留真实收款方与证据 | 转备款同时登记银行付款；只记备注 |
| 仅撤销错误认领 | 撤销客户分配，回到待认领或重新分配；公司现金不减少 | 把仍在银行的钱视为已退 |
| 重复记账纠正 / 真实退款 | 前者冲正多记事件，后者保留原收款并新建付款事实 | 删除原始收款抹去历史 |
| 发票或平台消耗同步 | 更新票据/履约/经营记录，与账关联 | 开票增加备款；消耗再扣已充值的资金总账 |

**计算基线。** 普通充值前返分支：现金本金＝广告币÷(1＋前返点数/100)，现金按该旧分支保留两位；8 点的示例为 1,000 元现金对应 1,080 广告币，不是乘 92%。丽人常见 8 点只是参考，前返后返通常在财务节点填写，不设全局固定 8。旧现金授信分支的后返货币＝现金本金×后返点数/100，保留三位；该输出不是等额已付人民币，后续折现金额按相应旧分支处理；不得将该分支扩大为全部产品。完整一类/二类、币种和舍入位置按 R05/R11/R14 的旧分支复算后发布模板。[R11、R14]

**欠款示例。** 循环信用批准 10 万，实际已用 8 万且无在途，则欠款 8 万、剩余可支用 2 万。客户实际回款 3 万核销后，欠款 5 万、现金备款 0、有效信用剩余 5 万。再回款 6 万，欠款清零、现金备款 1 万、有效信用恢复至 10 万。临时/单次不照此自动恢复，已偿部分退出。对于单一有效且未冻结的循环现金信用，可用授信＝批准上限−未偿本金−在途占用；发现异常负数必须暴露与处置，不能删掉债务使显示好看。[R08]

**尾差示例。** 应收 950.52 元、实收 950 元，匹配已发布规则或财务有据确认后，保留现金 950、接受短款 0.52、剩余待收 0；实收 951 时，保留现金 951、原应收 950.52、接受多款 0.48，不默认产生客户备款。原应收、实收和差额各自可查。模板未发布或超范围走财务人工处理，不要求每笔小额尾差找 Boss，不硬编码 1 元或 0.1 元阈值。现金来源 265.490 只能分配至该额，265.494 的差额不能通过尾差规则扩大实际现金来源。[R10、R11]

### 5.6 异常及边界

| 情形 | 处理规则与负责人 |
| --- | --- |
| 重复提交或并发操作 | 同一请求与事件只生效一次，返回原结果；前端按钮防重不能替代后端约束 |
| 渠道5万、两人各充4万 | 资金冻结原子完成，至多一笔取得执行权；不引入个人额度 |
| API 超时且平台可能成功 | 媒介核实原请求，未知保留在途；财务可查来源，不释放后再充 |
| 批次部分成功 | 每行/分段保存结果与金额，只结算成功部分，失败行独立重试 |
| 外部成功但CRM保存失败 | 进入待同步，持久化外部请求与证据；修复重放只补内部登记 |
| 外部已发生后补录且资金不足 | 记录真实发生日和登记日、欠款及异常；不再调平台，不伪造信用批准 |
| 区域未配或无有效办理人 | 进入主管/配置异常队列；保留申请及资金状态，不跳过节点 |
| 原办理人离职或协办到期 | 立刻禁止新操作，主管继承/重派；保留所有历史责任和操作记录 |
| 旧企微卡片批准被修改的申请 | 拒绝旧版本回调，要求当前有效版本审批；不重复加额 |
| 后台发布新流程/返点规则 | 新单新版本，在途默认原版；历史金额不被当前模板重算 |
| 银行同额多候选或代付 | 财务看真实付款人和依据，不能按最近时间自动误认 |
| 撤销已使用的收款分配 | 显示下游依赖，按事实走归属更正/欠款/退款，不删流水伪造余额 |
| 退款或后返已在外部支付 | 仅补付款事实与凭证，查重后核销，不能再次下发付款 |
| 已封存期间新增/更正 | 保留发生日与记账日；授权重开或调整期产生新版本及复查 |
| 公共资料合并/修改 | 预览账户、资金、合同及收益关系；身份冲突先核对，不按名字合并钱包 |
| 接口/通知失败 | 分别记录；通知补发不重做业务，审批未保存不能视为已生效 |

### 6.1 M01 个人工作台与任务中心

**优先级：P0　证据：R05 R04 R17**

**① 入口：** 工作台／我的待办。

**② 使用者：** 全体员工；主管；财务。

**③ 字段契约：**

| 字段 | 类型 | 必填/适用阶段 | 约束 |
| --- | --- | --- | --- |
| 任务ID | 标识 | 是 | 单据+节点+责任人唯一 |
| 业务单 | 引用 | 是 | 可回原单 |
| 当前节点 | 枚举 | 是 | 来自流程实例 |
| 下一步 | 文本 | 是 | 由状态与权限生成 |
| 责任人 | 人员 | 是 | 有效任职 |
| 等待时间 | 时间差 | 是 | 含数据截至 |
| 个人视图 | 配置 | 否 | 不覆盖组织默认 |
| 开户进度 | 申请级汇总 | 开户任务 | 成功/待办理/异常/纵横待补分列，均回原单 |
| 申请完成状态 | 枚举 | 开户任务 | 待办理/办理中/待确认完成/已完成，与行结果独立 |
| 角色视图 | 权限与显示配置 | 开户任务 | 商务关注关系与进度，主管关注队列与办理人，媒介关注本人申请与续办；同一applicationId |
| 本人未提交草稿 | 列表 | 本人身份 | 多份，创建人稳定身份隔离，负责商务不是草稿所有者 |
| 通知未读数 | 计数 | 个人通知 | 全部可见未读通知，开户按申请去重，范围与列表一致 |

**④ 业务规则：**

- M01-R01：一个待办对应原业务单及当前节点，多角色去重；查看和办理分别授权。
- M01-R02：工作台突出待补、未派、未知、同步失败及待付款，主管按地区看负载；通知已读不关闭待办。
- M01-R03：个人筛选、列顺序、密度、固定列可保存；动作返回后保持列表位置及筛选。
- M01-R04：开户待办按一张申请汇总，显示申请数量及成功、待办理、异常、纵横待补数量；5个账户仍是一项申请待办，点击返回同一原单逐行续办，不拆成5个丢失上下文的任务。
- M01-R05：已保存的账户结果离开或刷新后保留；再次进入工作台可从待办、异常、已办或资料待补返回原申请。纵横待补是资料状态，独立于开户成功和本次申请是否已完成。
- M01-R06：新申请的全部行录完后，工作台仍提示待确认完成，直到当前被指派媒介显式点击“完成本次开户”；历史已完成申请保留完成结果，不因新版规则重新产生未完成待办。
- M01-R07：工作台按当前角色组织同一申请：商务查看我发起/我负责申请，突出客户、主体、店铺与办理进度；媒介主管可按待指派/办理中/待确认完成筛选，突出当前办理人；开户媒介只将本人当前指派申请列为可办任务，突出申请账户数量、逐行结果汇总与续办入口。角色视图以同一applicationId稳定关联，不复制申请或改变归属；其他媒介在获准查看时只读，不能因可查看而取得办理权。
- M01-R08：批量录入和草稿保存始终归属同一开户申请；工作台仍以一申请汇总已成功、待办理、异常和纵横待补，不按本次勾选批次另建任务。保存10行草稿后退出，从原申请续填；选8行登记成功后另2行继续待办，不能据本批成功直接结束整单。
- M01-R09：未提交开户草稿按创建人稳定身份保存为多份，本人草稿列表支持继续、保存本份、另存一份及删除。创建人与负责商务分别记录，不按当前负责商务改移草稿所有者；保存本份不覆盖其他草稿，删除需确认或可撤销。已提交申请的行草稿继续归原申请，不与未提交草稿列表混同。
- M01-R10：开户通知按申请聚合一条并遵循角色相关范围：商务查看我发起/我负责的进度，媒介主管看派单跟进，开户媒介看本人办理申请；点击回同一原单。个人已读和状态变化提醒按M35管理，顶部未读数字与通知列表使用同一权限范围和未读口径。

**⑤ 状态与异常：** 待处理／处理中／待他人／已办；转派立即重算可办人，无人办理进入主管或配置异常队列。

**⑥ 验收：**

- M01-AC01 正向：一人兼两角色看到同一任务一次，可从下一步连续办理并回到原筛选。
- M01-AC02 反向/边界：已转派给他人的任务，旧责任人继续提交被拦截。
- M01-AC03 专项边界：申请5个账户，保存2个成功结果后退出；工作台仅显示1张原申请及2成功、3待办理，点击继续保留2个结果。
- M01-AC04 专项边界：全部5个结果保存后尚未点完成，仍有“待确认完成”入口；无后置节点时点完成进入已办；有后置节点时先待复核、后置完成后终结，之后可在已办与纵横资料待补回原单，不产生5个分散任务。
- M01-AC05 专项边界：同一申请分别用商务、媒介主管、被指派媒介查看，三个视图字段重点与操作不同，applicationId、客户/主体/店铺及已保存进度一致；主管三项状态筛选命中对应申请，其他媒介获准查看时没有办理操作且提交被拦截。
- M01-AC06 专项边界：人员甲保存草稿A和B，继续并保存A后B内容不变；A另存为C不覆盖A/B，删除C须确认或可撤销；人员乙的本人列表不显示甲的草稿，修改负责商务也不转移创建人。
- M01-AC07 专项边界：提交草稿A成功只移除A，B保持；提交失败A保留。可可靠定位原商务的历史全局草稿归回原商务，未知归属草稿保持待核对，不被当前人认领或删除。
- M01-AC08 专项边界：同一开户申请多次逐行更新，通知列表只有一条当前申请通知；甲已读不改变乙未读，顶部数字等于当前身份通知列表的全部未读条数，开户按申请去重计数。

### 6.2 M02 公共客户检索与查重路由

**优先级：P0　证据：R01 R02 R05 R17**

**① 入口：** 公共资料／全局搜索。

**② 使用者：** 商务；媒介；资料管理员。

**③ 字段契约：**

| 字段 | 类型 | 必填/适用阶段 | 约束 |
| --- | --- | --- | --- |
| 客户ID | 标识 | 是 | 稳定内部ID |
| 客户名称 | 文本 | 是 | 用户自定义名称、规范化查重 |
| 普通/渠道 | 枚举 | 是 | 非权限角色 |
| 所属主体 | 引用列表 | 否 | 选客户即完整展示已关联主体；空搜索可见，名称/信用代码筛选 |
| 检索命中类型 | 枚举 | 是 | 客户/主体/店铺/账户 |
| 规范化名称 | 文本 | 是 | 保留原名 |
| 联系人 | 文本 | 否 | 字段权限 |

**④ 业务规则：**

- M02-R01：先搜索后新增，同名客户不重复建立；空白清理等规范化规则保留原名，近似名称只提示候选。
- M02-R02：名称已存在时可复用资料；确需新增不同业务档案须使用不同名称，不以改名自动判为不同法律实体或独立资金。
- M02-R03：路由展示完整路径及命中原因；公共资料可检索不暴露未授权资金、薪酬、他人账户办理入口。
- M02-R04：客户下可有多个主体；新建主体明确所属客户。主体保留既有customerIds共享引用，不由客户1:N反推主体只能属于一个客户；公共搜索不授予归属或资金操作权。

- M02-R05：在开户页的客户—主体选择器中，未选择客户时不展示主体候选；选择已有客户后立即完整列出该客户已关联主体，搜索框为空也显示，不截断为前10条；可按主体名称或统一社会信用代码筛选。
- M02-R06：在开户页的客户—主体选择器中，当前客户没有主体或筛选无匹配时明确显示对应空态；全局已有主体查重结果单独列为“全局已有主体（尚未关联此客户）”，不得混入本客户主体或自动关联，只有用户选择复用时才新增当前客户关联，保留既有customerIds引用。
- M02-R07：在开户页的客户—主体选择器中，选择客户后，主体搜索为空也可进入同页新增主体；保存前按主体名称及可靠信用代码查重，命中已有资料时引导选择复用，未命中才新增并关联当前客户。独立全局检索仍可直接搜索主体、店铺和账户，不要求先选客户。

**⑤ 状态与异常：** 草稿／有效／停用／历史待核对；多路径不自动取第一条。

**⑥ 验收：**

- M02-AC01 正向：同主体被A、B复用时，展示各自账户与授权动作，能从命中店铺继续开户。
- M02-AC02 反向/边界：并发创建同名客户只有一条成功，另一条返回已有记录入口。
- M02-AC03 专项边界：客户已关联12个主体，选客户后不输入搜索即可看到全部12个；按名称或信用代码筛选后再清空搜索，恢复全部12个。
- M02-AC04 专项边界：本客户无匹配而全局命中时分区提示尚未关联；查看或输入搜索不修改关系，显式选择后才关联并复用，不复制主体。

### 6.3 M03 主体、店铺与本地推平台资料

**① 入口：** 客户全景／主体详情／店铺详情。

**② 使用者：** 商务优先维护；媒介在原申请有权新增、补全和更正；资料管理员。

**③ 字段契约：**

| 字段 | 类型 | 必填/适用阶段 | 约束 |
| --- | --- | --- | --- |

| 统一社会信用代码 | 文本 | 按资质阶段 | 字符串与可靠证照查重 |
| 店铺ID | 标识 | 是 | 唯一店铺自动展示复用；无店同页新增；历史多店待核对 |
| 店铺名称/来客名称 | 文本 | 是 | 自定义真实店名，填写一次 |
| 直客ID | 主体资料 | 否 | 主体当前1:1直客；同主体账户共享 |

**④ 业务规则：**

- M03-R05：历史同主体多店或不同直客值标“历史关系待核对”，保留原行、原值和关联；不得自动取第一条、合并、删店或伪称已迁移。
- M03-R06：营业执照、行业、银行、地址及联系信息按产品材料与阶段规则采集；缺少可后补材料不伪造文件，不把来客ID或直客ID变成开户完成门槛。
- M03-R07：选择主体后立即查询该主体店铺：有唯一当前店铺时自动展示并复用，无店铺时明确提示并提供同页新增；历史存在多店时逐条保留并显示“历史关系待核对”，不得自动选择第一店或绕过冲突新建第二店。
- M03-R08：信用代码、来客ID和主体直客ID按身份规则校验，不因licenseEvidence或流转备注为空拦截保存；证照来源说明如保留为可选资料，不冒充真实附件或已核验结果。材料是否必需仍按已发布产品规则，不能用文字备注代替必需文件。
- M03-R09：行业从后台已启用行业字典搜索选择；后台授权人员可新增、修改、启用、停用。停用后不供新选择，已有资料和历史快照仍保留原值并明确状态，不自动清空。
- M03-R10：页面明确标注“店铺名称（来客名称）”“来客ID（选填）”“主体直客ID（选填）”；不以开发术语、评审提示或来源核验任务代替业务字段说明。

**⑤ 状态与异常：** 资料待补／待核验／有效／冲突；资料状态不等于开户结果。

**⑥ 验收：**

- M03-AC01 正向：同主体申请两个账户，共享一个直客及一个店铺来客；主体名与直客名、店铺名与来客名分别一致，两个ID可同时为空。
- M03-AC02 反向/边界：新建关系给已有主体添加第二个当前店铺，或给主体另建第二份直客时被拦截；历史多店保留并提示核对，不静默合并。
- M03-AC03 专项边界：更正主体名后当前直客名称随之展示新值；原申请和执行快照仍保留旧名与原文件。
- M03-AC04 专项边界：选择仅有一家店的主体，已有店铺立即展示且复用原ID；选择无店主体可同页新增；选择历史多店主体显示冲突，未自动选中第一店。
- M03-AC05 专项边界：已有主体补信用代码、店铺来客ID或主体直客ID，流转备注与证照来源说明均留空时可按身份规则保存；审计仍含操作者、时间及前后值，必需附件仍单独校验。
- M03-AC06 专项边界：后台停用某行业后，新选择不再显示该项；原主体与旧申请仍保留原行业，字段标签清楚区分店铺名称和来客ID。

### 6.4 M04 供应商、端口与办理能力

**优先级：P0　证据：R05 R02 R17 R18**

**① 入口：** 公共资料／供应商；开户选择。

**② 使用者：** 媒介；供应商管理员；财务按字段权限。

**③ 字段契约：**

| 字段 | 类型 | 必填/适用阶段 | 约束 |
| --- | --- | --- | --- |
| 供应商ID/名称 | 引用/文本 | 是 | 稳定身份 |
| 代理商外部ID | 文本 | 条件 | 平台命名空间 |
| 支持产品 | 列表 | 是 | 能力匹配 |
| 端口 | 引用 | 条件 | 不冒充媒体类型 |
| 供应商收款账户 | 子表列表 | 收付款业务需要时 | 保留多账户、账户类型、户名、账号、开户行和有效版本 |
| 动作能力 | 枚举 | 是 | API/人工/待接入/不适用 |
| 有效期 | 日期 | 否 | 过期不可新选 |
| 平台代理商名称 | 文本 | 按已核实来源 | 与CRM供应商名称、代理公司法定名区分 |
| 平台范围 | 媒体引用 | 外部代理ID存在时 | 限定代理ID命名空间，不代替支持产品和动作能力 |
| 开户行/支行名称 | 账户资料 | 银行卡按业务需要 | 旧bankname，不与地址混用 |
| 开户行地址 | 文本 | 否 | 未定位旧独立结构，不推定可自动迁移 |

**④ 业务规则：**

- M04-R01：供应商按本次开户或账户服务关系选择，不锁死主体；可推荐同主体同产品最近成功且有效的供应商。
- M04-R02：平台、产品、接入方式、供应商、端口、对象类型分别记录；不由dy_agentId或旧入口判断媒体。
- M04-R03：能力按产品×供应商×对象类型×动作配置，查余额可用不代表充值自动可用。
- M04-R04：开户流程只选择适用供应商并只读引用已有资料，不在开户页编辑或补填供应商银行资料。银行资料在独立供应商档案按字段权限维护，不作为每次开户的默认录入门槛。
- M04-R05：旧dig_supplier.supplier_name承载CRM供应商名；媒体端口agent_name、corporation_name等仅是平台代理名称候选。外部代理ID来自dig_dy_developinfo.agent_id或dig_kuaishou_jinfu.agent_id；dy_agentId/ks_agentId是内部端口引用，不可冒充外部ID。
- M04-R06：旧供应商平台/账户类别见dig_supplier.types、account_type及端口关联；本次统一平台范围属于归一化表达，必须逐来源核对，不宣称旧库已有同名自由文本字段。
- M04-R07：旧dig_supplier_account通过supplier_id关联多条收款账户，保存account_no、account_name、bankname、account_type。银行卡、支付宝、微信分型，账号不是银行机构行号；不得把旧多账户压成一个永久覆盖的银行字段。
- M04-R08：独立银行网点地址未在旧供应商账户结构中定位；bankname是开户行/支行名称，不是地址。确需新增地址时按可选新字段说明来源，不能从支行名猜出地址或宣称旧字段已迁移。
- M04-R09：供应商账户新增、更正、停用保留版本及权限控制，历史执行/付款引用当时有效资料；选中账户不等于实际付款，供应商收款资料不与主体登记银行、客户付款账户或公司自身银行合并。

**⑤ 状态与异常：** 草稿／有效／停用；旧单保留原服务与版本。

**⑥ 验收：**

- M04-AC01 正向：同主体在两个供应商新开不同账户，历史账户不被修改。
- M04-AC02 反向/边界：停用或不支持当前产品的供应商不能被新申请提交选中。
- M04-AC03 专项边界：开户选择已有供应商，页面不出现供应商银行编辑或必填项；供应商主档两条不同收款账户均保留，按实际业务选择版本，不覆盖成一条。
- M04-AC04 专项边界：内部dy_agentId与外部agent_id数值不同，界面不得互换；开户行只有支行名时不生成银行地址，不把未知地址写成已迁移。

| 平台+真实广告账户ID | 文本 | 成功时 | 真实身份唯一 |
| 账户名称 | 文本 | 否 | 自定义，可空，非查重唯一键 |
| 产品/办理方式 | 枚举 | 是 | 独立字段 |

- M05-R02：重复真实广告账户ID提示并拦截，不能用旧自有/外转入口、供应商另造唯一空间；历史冲突先核定不自动合并余额。
- M05-R03：资料页展示全路径、平台资料、责任协作、服务结算与原单；不因列表展开泄露字段权限。
- M05-R04：纵横为空可完成开户与充值；已填时一对一校验，补资料不改变归属。
- M05-R05：账户名称自定义且非必填；空名称仍显示完整账户ID并可完成开户。账户详情的直客展示引用主体，编辑入口回到主体维护，不提供账户独立直客或直客名称输入。
- M05-R06：已成功账户可从账户详情与已办申请回到原开户单；显示开户成功状态和纵横待补状态。补纵横保持原账户ID、成功事实、负责商务与原申请，不重新开户、不重新产生整单办理任务。

- M05-AC01 正向：同主体两条账户展示同一主体直客，一条名称为空仍可通过完整ID定位并展开申请、来客、纵横及责任。
- M05-AC02 反向/边界：在另一旧入口提交同平台同号仍被拦截；无权限用户无法导出隐藏资金列。
- M05-AC03 专项边界：完成开户但纵横为空，账户仍显示成功且可在已办原单后补纵横；补值后账户身份、归属和原成功状态不变。

### 6.6 M06 开户申请、预审与逐行办理

**① 入口：** 账户列表新增开户／工作台快捷入口。

| 负责商务/实际提交人 | 人员 | 是 | 分别记录 |
| 区域 | 枚举 | 是 | 路由主管 |
| 营业执照和资质文件 | 文件版本 | 按产品材料规则 | 显示/必需/可后补，真实文件预览 |

| 外部请求/凭证 | 引用 | 执行时 | 真实成功依据 |
| 纵横ID | 文本 | 否 | 可后补，非空一对一 |

| 完成本次开户 | 申请动作 | 全部行成功或明确取消后 | 被指派媒介显式确认，纵横可后补 |

**④ 业务规则：**

- M06-R01：商务原前三步合并为一页：搜索查重客户并选择/新增，原地维护主体和唯一店铺，填写产品责任及资料，选择数量并提交；商务不展示逐行账户或按行直客编辑。返回和原地维护不丢输入，提交后留在原模块原单。
- M06-R02：营业执照及资质按已发布的产品、材料类型和阶段规则校验。可后补材料可继续预审；需在执行前补齐的材料未满足时不得执行。来客ID、直客ID和账户名称均不成为完成必填。
- M06-R03：只有具备媒介主管权限的角色才能按区域派单或重派；派单不是审批。普通媒介只能办理当前指派给本人的任务，不能自行派给自己、替他人提交结果或完成整单；主管亲自办理也须具备办理权并被指派。普通开户不额外要求Boss、财务或有效合同。
- M06-R04：申请明确负责商务；保存数量、提交资料、附件及配置快照。媒介按数量在原申请表格录入并逐行或批量登记，成功后各户继承申请归属，实际点击者不自动取得归属。
- M06-R05：每行保存未提交、执行中、成功、失败、未知、取消及待同步；外部成功CRM失败只补同步，只重办明确失败行，重复同请求返回原结果。
- M06-R06：当前被指派媒介在本人原单内按字段权限维护主体、店铺及其直客/来客ID；普通维护的流转备注选填。当前资料、申请快照和执行快照分开，关键变更按影响重新校验，通知相关商务并留痕。
- M06-R07：同主体多行共享主体直客，不再按直客ID取得一户专属占用；每行真实广告账户ID仍按平台身份防重，纵横非空一对一独立校验。
- M06-R08：增加数量生成空白媒介办理行；缩减只能移除未受理未执行的尾部行，已受理、成功、未知或待同步行不因减号消失。新行不复制广告账户ID、纵横ID和外部执行结果。
- M06-R09：上传前先选择主体，附件元数据保存subjectId；切换主体解除本申请原附件关联并提示重新选择，保留已提交历史快照。提交或新的外部执行前发现跨主体附件必须拦截；未知/成功待同步仍处理原请求，不伪造新执行。
- M06-R10：未选择客户时不展示主体候选；选择已有客户后立即完整列出该客户已关联主体，搜索框为空也显示，不截断为前10条；可按主体名称或统一社会信用代码筛选。
- M06-R11：当前客户没有主体或筛选无匹配时明确显示对应空态；全局已有主体查重结果单独列为“全局已有主体（尚未关联此客户）”，不得混入本客户主体或自动关联，只有用户选择复用时才新增当前客户关联，保留既有customerIds引用。
- M06-R12：选择客户后，主体搜索为空也可进入同页新增主体；保存前按主体名称及可靠信用代码查重，命中已有资料时引导选择复用，未命中才新增并关联当前客户。
- M06-R13：选择主体后立即查询该主体店铺：有唯一当前店铺时自动展示并复用，无店铺时明确提示并提供同页新增；历史存在多店时逐条保留并显示“历史关系待核对”，不得自动选择第一店或绕过冲突新建第二店。

材料规则的执行位置为申请提交或媒介执行。默认营业执照和其他资质均可选；发布者可按产品及材料类型调整，不擅自增加全产品强制门槛。实际文件存在当前浏览器IndexedDB，原单记录存储键及元数据快照，可预览/下载。未知或外部成功待同步继续核实或补同步，不因后来新增材料规则重发开户请求。[R17]

### 7.1 关系图与核心约束

**图 7-1　账户与公共资料关系**

![图 7-1 账户与公共资料关系](assets/fig-7-1.png)

图7-1为V1.5沿用的目标关系：客户1:N主体；主体1:1店铺、1:1直客资料，同时主体1:N广告账户。直客名称等于主体名，直客ID可空且由同主体多账户共享；店铺名等于来客名，来客ID可空。纵横仍是账户独立非空一对一字段。历史冲突单列待核对，不自动迁移，也不据关系合并资金。[R17、R05、R06]

**图 7-2　资金对象与可追溯分录**

![图 7-2 资金对象与可追溯分录](assets/fig-7-2.png)

图 7-2：一个收款事实可有多笔分配；一个业务单可产生多个不同语义但唯一的事件；事件的全部分录原子保存。原始来源和账内余额都进入对账，不能只做内部表间相等检查。[R10]

| 对象/稳定主键 | 关键字段与关系 | 约束与生命周期 |
| --- | --- | --- |
| 公共客户 customer_id | 名称、规范化查重键、普通/渠道标签、来源、关联主体 | 同名新建拦截；共享引用不建立钱包操作权；停用保留历史 |
| 主体 subject_id | 客户引用、法律名称、信用代码、证照、直客ID、地址、联系人、旧ID映射 | 可靠证照查重；客户1:N主体；主体当前1:1店铺及直客、1:N账户；历史多店待核对 |
| 店铺 shop_id | 主体、店名即来客名、产品适用资料、可空来客ID、核验状态 | 主体当前一个店铺；一店一个可空来客ID；不据号长识别，变更保留历史 |
| 广告账户 account_id | 平台、完整外部ID、产品、办理路径、店铺、归属商务 | 真实平台身份唯一；跨入口/供应商同号必须提示拦截，跨平台命名空间由平台契约定义，不擅自全平台混同 |
| 平台专有资料 | 来客→店铺；直客→主体；纵横→账户；名称派生与来源 | 直客ID可空且同主体多账户共享，直客名=主体名；来客名=店铺名；纵横非空账户一对一可补 |
| 账户责任/协办关系 relation_id | account_id、负责商务、有效起止、协办授权、变更原因 | 申请阶段有业务责任，成功落档；历史操作及收益快照不覆盖 |
| 供应商服务关系 service_id | 账户/申请、供应商、产品能力、生效区间 | 开户逐次选择；不锁在主体；变更需可执行能力与流转记录 |

### 7.2 数据规范

平台编号、证照和银行账号使用字符串，保留原始值与清洗后查重值；不设未经证实的固定位数，不使用浮点或科学计数法存 ID。金额采用精确十进制、显式单位和分支舍入，旧三位小数不统一截两位。所有计算记录模板版本、输入值、换算基数和舍入位置。

记录真实发生时间、系统登记时间、审批/执行时间、业务期间与业务时区。迁移同时保留旧入口、旧表主键、旧分类、来源文件/批次及映射依据，禁止只留新 ID。名称、人员和模板变更不反写历史快照。停用、合并、更正须有引用处理策略，不能物理删除已参与业务的事实。

### 12.2 灰度与放行

灰度按完整业务闭环及资金范围切换，避免同一钱包/账户同时被两套系统写入。每批记录范围、旧系统写入口控制、期初、在途、外部请求、回退触发及实际观察结果。批次大小和观察窗口由真实容量、业务节奏与验收结果确定，不机械照抄模板的 5%→50%→100%。

放行至少满足：账户关系无未解释冲突；同一资金范围重算与来源覆盖通过；重复/并发/未知/部分成功可恢复；授权及离职交接生效；财务能定位每笔事实及差异；旧7类产品入口所涉及业务有已验证兼容路径。新接口未验证的自动动作不进入本批自动执行范围。

### 12.3 回滚四要素

- 数据：保留切换映射、校验快照和新增事件；生产已发生的新收付款/平台事实不可用旧备份抹去，必须先对账和补记。
- 流量：按获批范围关闭新写入并切换唯一执行入口；只读查询可保留，避免两套同时提交。
- 在途单：停止新派发，保留外部请求、冻结与未知结果；指定承接系统与责任人，仅核实/补同步，不新充新付。
- 归档：保存切换批次、前后版本、操作人、原因、差异与复查结论。重新切换需新验收记录。
